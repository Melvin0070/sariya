Sariya, end to end

The whole product loop, every branch the app actually handles, who it is for, why each design choice is there, and how to show it to a cold jury in 3 minutes 30.

The steel inside an Indian house is visible for a day or two, then the concrete hides it for good. Sariya checks it with one phone and a printed card, offline, and leaves a record the responsible engineer signs.

The pitch line that carries the architecture: AI finds the bars, maths measures them, rules decide. Only one stage is a neural network (bar pixels, on the NPU). Every millimetre on screen comes from the card's geometry, and every verdict comes from a versioned rule file you can read.

People and phones

Four humans, three phones and a laptop. Each phone is set to one role at setup, and the role decides which files it will open. This is a product decision, not a demo convenience: the person being checked must never be the person who sets the bar or the person who approves.

End-to-end workflow

Each stage below says what the user sees, what the app enforces, and the reason. Screen names in grey match the app's routes so the team can find them.

0

Setup and key enrolment (once per phone)

setup.tsx · keys.tsx · qr.tsx?mode=enrol

Pick a role (operator, engineer, verifier), enter a name, set a PIN. The phone makes an Ed25519 key pair kept in SecureStore. A readiness screen checks camera, Hindi and Kannada voices, the signing key, storage, and which accelerator the model loaded on (NPU, else GPU, else CPU, with the reason). Then phones scan each other's key QR under Settings › Trusted phones; trusting a key asks for the PIN.

WhyTrust is explicit and local. A key that arrives inside a file is never trusted on its own, so a forged pack can't bring its own "engineer". The readiness screen exists so a GPU fallback or a missing voice is found in the pit, not on stage. PIN replaced fingerprint because the loaners have none enrolled; a device-bound biometric key is the product version.
1

Spec in: the engineer sets the bar

P2: issue.tsx (Send drawing values) · P1: received.tsx → new inspection

On P2 the engineer picks Slab, names the member ("Slab S1"), and enters six fields: bar diameter, main count and spacing, distribution count and spacing, bottom cover. Empty means "not on the drawing" and is never filled with a default. P2 signs a sariya.spec/1 file and shares it through Office Kit. P1 opens it from the system file picker; it is accepted only if signed by an enrolled engineer key, is complete, in range, and for a member this build supports. Opening the same file twice returns the same inspection.

Fallbacks on P1: type the values (the review then says "typed on site" and the engineer must also tick "the drawing values match my drawing"), use the DEMO PROP preset (marked as such), or choose no drawing for measure-only mode: values, no verdicts.

WhyWithout this, the operator types the spec they are judged against and could loosen it. With it, any edit drops the signature, and if values differ from what the engineer signed, approval is blocked outright. A judge will ask "who sets the spec?"; this is the answer on screen.
2

Live scan

inspect/summary.tsx → inspect/scan.tsx

The operator lays card S (90 mm ChArUco) flat on the mesh, torch on, phone at about 30 cm, and picks a target: main bars, then distribution bars. Every frame: OpenCV finds the card and computes a homography (pixels to millimetres on the card plane); the U-Net on the NPU marks bar pixels; the mask is warped onto the card plane and summed into a profile whose peaks are bar centrelines; gaps are drawn back onto the preview as lines with "~50" labels. Status chips guide the hand: "Find card S", "Show all of card S", "Blurred: hold still", "Turn the phone so the bars run up the screen", then "Ready to lock" with a haptic.

Bars seen only in part (usually under the card) are drawn dashed amber and never counted.

WhyA single camera has no scale. The printed card supplies it to millimetre level; ARCore tracks to centimetres and was dropped. Live lines make the system legible: the jury watches a line follow a bar the judge moves, which is more convincing than any accuracy slide. The "~" says this is guidance, not a measurement.
3

Lock

scan.tsx Lock button → frozen evidence + lock sheet

Holding Lock collects about 1.2 s of frames. Frames under 70% of the sharpest are dropped; the most common bar count wins; each bar takes its median position. The band is the larger of 5 mm and 2 × √(frame scatter² + mask-edge error² + 1% scale). The frozen frame is saved with the model's own lines, a coverage map (frame footprint, card outline, bars used, partly seen bars, in card mm) and the engine string (seg v2 7ad05e742fad · NPU · 20 ms).

If fewer than the minimum sharp, agreeing frames exist, the lock carries a gate: a reason in words and an action ("Only 4 sharp, steady frames agreed on the bars (3 blurred). Hold still until it says Ready to lock"). If detection stays shaky, mark by hand: freeze a frame, tap the card corners and each bar; same geometry, same gates, labelled "marked by hand".

WhyVerdicts only from immutable, quality-gated evidence. The band is not divided by √15 because frames from one hold share the same systematic error; pretending otherwise would shrink the band dishonestly. The 5 mm floor stays until tape checks justify less.
4

Readings by hand

inspect/readings.tsx

Cover: tape reading entered on the phone; within if between the drawing value and +10 mm. Bar size: a 200 mm offcut on a kitchen scale; mass per metre is matched to IS 1786 bands (10 mm: 0.574–0.660 kg/m, 12 mm: 0.844–0.932). Each can be marked "not visible". Hooks (135° template) appear only for beams whose drawing asks for them, so not in this build.

WhyA camera at arm's length can't separate 10 from 12 mm reliably, and bottom cover is hidden. Prompting for a cheap physical reading is more honest than a confident guess, and the weigh test also catches underweight or fake steel, which passes every geometry check.
5

Decide

lib/rules.ts · inspect/summary.tsx checks sheet

Six checks for a slab: count and spacing for each bar family, cover, size. Proposed limits (an engineer must confirm, since IS 456 gives no placement tolerance): mean spacing ≤ spec + max(10 mm, 5%), any single gap ≤ spec + max(15 mm, 25%), count equals the drawing. At the stage spec of 50 mm: mean ≤ 60, any gap ≤ 65. A value is outside only if its whole band clears the limit, within only if its whole band is under it, otherwise re-scan. There is no overall badge; the summary is a tally such as "4 of 6 within limits · 1 outside · 1 needs a reading".

WhyDeterministic rules are auditable: each finding carries its rule ID, the exact numbers and the rulebook version. No model is allowed to decide, word, or recompute a verdict. "Never PASS, never safe" keeps liability where it belongs, with the engineer who signs.
6

Tell the mason, fix, re-scan

inspect/fix.tsx

For each outside finding the rule engine produces a typed fix (add bars, move bar, add in gap, respace, cover low/high, size). A template turns it into a sentence in Hindi, Kannada or English, played with the offline system voice, auto-played once, with stop and repeat and subtitles always on. Example (F2): "Teesra gap assi millimetre hai. Drawing mein pachaas hai. Is sariya ko andar khiskao." After the fix, the operator re-locks that target; the newer lock supersedes the old one.

WhyThe number is the instruction. A mason who hears "gap 3 is 80, drawing says 50, slide this bar in" can act without reading English or a drawing. The fix logic tells a moved bar (one wide gap next to one narrow, summing to two spacings) from a missing bar, so it says "move" rather than "add steel".
7

Sign and send the capture

inspect/sign.tsx → share sheet / folder

The operator signs. The signed payload is exactly: active locks with values, bands and image hashes; the spec revision (including the engineer's signed issue if present); manual readings; rulebook version; engine. Anything still unchecked is recorded as "not checked before signing", never as within. The .sariya.json pack, with evidence photos embedded, goes to the system share sheet (Office Kit is a share target). Android can't report delivery, so the app asks the operator to confirm it arrived.

WhySigning locks the evidence, not a screen. Any change to a value, the spec or a photo changes the hash and breaks the signature.
8

Engineer review and decision

P2: received.tsx → review/[key].tsx

On open, P2 checks in order: pack complete → hash matches body → signature matches named key → not already processed → not signed by this phone → every evidence photo matches its hash → signer enrolled as an operator. Only then does the review open. It shows the frozen frames with lines, the coverage map, each value ± band with its source, readings, and a spec-origin banner: issued by you · unchanged, issued by another engineer, typed on site, or differ from the issued ones (approval blocked).

Approve needs "I reviewed" ticked, plus "the drawing values match my drawing" when someone else set them, then the PIN. The sign-off QR appears on P2 immediately; the approval file goes back to P1. Or Ask for another view: pick checks, add a note, sign a request.

WhyTwo phones, two keys: the same key can't capture and approve. The engineer signs the capture hash, so the approval can only ever attach to that exact revision. Remote review is the point: the engineer who can't attend every pour can still look at the actual frames.
9

Close the loop

P1: received.tsx → record/[key].tsx · P3: qr.tsx?mode=verify

P1 opens the approval: it attaches only if a record with that exact capture hash exists, and the record now shows "Approved by Er. … " with the QR. If a request comes back, P1 opens rev n+1 carrying everything except the requested checks, which must be scanned again; the old revision stays as history with its own signature. P3 scans any sign-off QR and gets "Valid · Er. name · Slab S1 · rev 1 · approved …" against its enrolled engineer keys, with no network.

WhyThe record has to be checkable by people who will never open the app on a laptop: the owner, a lender's valuer, the mason who wants proof the fix was approved.

What the trust layer does not prove

It is tamper-evident, not tamper-proof. It doesn't prove which physical slab was scanned or what was finally poured, and a key in an app is not a professional licence. Say this before a judge does.

User stories

Each story lists the acceptance criteria the current build meets. The last two are the payer stories that shape the business, not the demo.

Responsible engineer

As the engineer who signs, I want to send the drawing values myself, so the person being checked can't set a looser bar.

  • Signed spec file, accepted only from my enrolled key
  • Any edit shows on my review; changed values block approval
Responsible engineer

As an engineer who can't attend every pour, I want to see the actual frames with the measured gaps, so I can approve from my desk.

  • Frozen frame with model lines and gap labels; coverage map
  • Value ± band with source (camera, hand-marked, tape, scale)
  • Approve with PIN or ask for another view of named checks
Operator

As the site engineer the evening before the pour, I want count and spacing measured in seconds, so I can check every critical patch, not a sample.

  • Live lines and ~mm, Lock in about 1.2 s
  • Works offline in airplane mode
  • Hand-marking fallback if the model is unsure
Operator

As the operator, I want the phone to tell me when it isn't sure and what to do, so I never sign a guess.

  • Re-scan with a reason and an action in words
  • Partly seen bars never counted
  • Unchecked items recorded as such at signing
Mason

As the mason, I want the fix in my language with the number, so I can correct the steel without reading a drawing.

  • Hindi or Kannada audio, subtitles, repeat
  • "Move this bar" vs "add a bar" correctly told apart
Operator

As the operator, I want to catch wrong-size or underweight steel without a lab, so substitution is found before it's buried.

  • 200 mm offcut on a kitchen scale → IS 1786 size band
Owner / verifier

As the house owner, I want to check that a real engineer approved this exact record, without an account or internet.

  • QR verified offline against enrolled engineer keys
  • Altered or unknown-key QR is called out
Engineer (protection)

As an engineer exposed to liability, I want a dated, signed pre-pour record that can't be silently edited or re-used.

  • Hash-bound evidence, two keys, replay rejection, revisions kept
Steel or cement brand (payer)

As a brand's technical services lead, I want each free slab visit to produce a signed, measured report, so one engineer covers more sites and the visit builds trust in the brand.

  • Roadmap: branded report, slab-date leads, rib-mark brand check
Builder / lender (payer)

As a builder releasing stage payments, or a lender releasing a tranche, I want evidence that the steel matched the drawing before I pay.

  • Roadmap: QR on the stage-payment or tranche form; lenders buy the evidence layer only

The demo

3:30, cold jury, airplane mode, half-scale props: 28 × 28 cm 5 × 5 mesh of 8 mm bars at 50 c/c both ways, every bar movable; card S on the mesh; a "12" labelled 10 mm offcut and a kitchen scale; gloves. Three roles on stage: A presents and never touches a phone, B operates P1, C is the engineer on P2 with the laptop mirror. J is a judge who volunteers.

Why this order

  • Product quality (30) and demo (10) are judged cold, so the first minute is a real fault, made by a judge, found by the phone, confirmed by a tape. A judge's own hands are the strongest proof that nothing is staged.
  • Novelty (20) lands on the abstention beat and the two-key sign-off: the things other camera tools don't show.
  • Technical depth (15) is the numbers screen and the trust checks shown working, not described.
  • Phone use (15) and Office Kit (10) are scored by device data, but the jury should also see camera, voice, NPU and the Office Kit desk in action.

Pre-flight (T-60 to T-2)

  1. Install the release build on P1, P2, P3. Clear app data from earlier tests (P1 holds test drafts).
  2. Set roles: P1 operator, P2 engineer ("Er. C"), P3 verifier. Set PINs. Enrol keys both ways (P1↔P2, P3 trusts P2).
  3. Readiness on every phone: model on NPU, Hindi voice present, key present.
  4. T-50: on P2, send drawing values for "Slab S1" (8 mm, 5 bars @ 50 both ways, cover 20). Open on P1. Confirm it reads "Drawing values received".
  5. Prepare the replay: one earlier capture already approved on P2, with its pack file in the laptop's transfer folder.
  6. Run the CONTROL scan once: all within. Torch on, check glare on the card under the hall lights.
  7. Airplane mode on all phones; Office Kit mirror of P2 on the projector; P3 charged as hot spare.

When the demo breaks

The rule: name it, show the fallback, move on. Never debug on stage. Each recovery under 20 s.

The five hostile questions most likely to come

QuestionAnswer
"So you certify it's safe?"No. It measures what's visible and records it; the engineer signs.
"Japan already does this."Yes, which is why we trust the physics. We built it for India's self-built pour: offline on a phone, IS-code rules that abstain, the fix in Hindi or Kannada, a signed record.
"Who sets the spec?"The engineer signs the drawing values and sends them. If the operator changes one, approval is blocked.
"Scan a good cage, pour a bad one?"Duplicate records are rejected and the engineer can ask for another view, but nothing proves what is poured. Tamper-evident, not tamper-proof.
"What needs the NPU?"Live lines every frame: ~20 ms on the NPU in the app, 235 ms on the CPU in the benchmark. The readiness screen shows which ran.
