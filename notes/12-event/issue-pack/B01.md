## Work

- First audit existing app repo/branch/APK and completed gates; link any work already done instead of rebuilding it. This planning repo has no app source at the time of issue creation. Record the implementation repo and app root in the control issue.
- Create or verify one Kotlin/Compose :app module, in.sariya.camera, minSdk 31. Resolve and pin a buildable dependency set; old prompt versions are candidates, not proof that Maven artifacts exist. Do not add every optional runtime.
- Freeze SpecRevision, AnalysisFrame metadata, LiveFrameResult, LockResult, Finding/FixAction, ScanRecord and TelemetrySample. Include frame/lock IDs, timestamps, image dimensions, crop/rotation/coordinate transforms, mm units, family IDs, card/calibration ID, gate reasons, uncertainty terms, rulebook version/hash and actual accelerator.
- Keep live approximate results separate from immutable locked measurements. Freeze spec and asset versions into a lock; a changed spec cannot silently change a signed record. Export fake results and small golden JSON fixtures for other lanes, visibly marked as fixtures.
- Freeze VerificationState, ApprovalState, TransferState and ReviewRequest adapters plus fake states at contract freeze, before the trust implementation. LockResult always identifies its actual measurement/evidence mode; Sabari records the selected stream/still branch before B06/B07 bind to it.
- Share a development signing certificate securely across laptops; never reuse or publish a production key. Preserve existing installs and Android Keystore identities. Keep this APK certificate distinct from capture/approval record keys.
- Add minimal crash-to-file and copy-diagnostics support now, so Red debugging needs no ADB. Wire permission-denied, model-missing and startup-error states.
- Create AGENTS/CLAUDE instructions, issue-sized branches/worktrees and local prompt files. Melvin alone integrates shared contracts and root build changes. Set up build/JVM checks if the repo supports CI; include an offline build after dependencies are cached.

## Acceptance

- [ ] A clean checkout builds and runs JVM tests with pinned dependencies; a subsequent cached build succeeds offline.
- [ ] Serialized fixtures round-trip with stable IDs/units. A fixture is never displayed as a real scan or included in accuracy metrics.
- [ ] An APK from the second laptop updates the first without uninstalling; stored data and enrolled record keys survive.
- [ ] Reject stale lock/spec IDs at the interface boundary and retain actionable diagnostics after a simulated controlled error.

**Loaner check:** Install the same integration APK on P1/P2/P3; open the fake-data screen, deny/regrant camera permission, and copy a diagnostic report.
